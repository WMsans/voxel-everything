# 60 fps at render scale 65% / near field 40% — design

**Date:** 2026-09-08
**Target machine:** Apple M1 (base, 8 GPU cores), 2560×1440 @ 144 Hz, macOS, Metal, Godot 4.7.2
**Config under test:** `--render-scale=0.65 --near-scale=0.40` → 1592×857 internal 3D

## Goal

`p99 < 16.6 ms` on five benchmark legs: **steady, move, ridge, edit-bounded, island**.

The **edit** leg is explicitly out of scope for the 60 fps guarantee (it fires the edit tool
every single frame against a 907-chunk collider backlog; it is a stress test, not gameplay).
Its worst stalls are still in scope as bugs, but no frame-rate promise attaches to it.

Image quality is to be held constant wherever possible. Quality reductions are a *fallback*,
taken only when a matched-image optimisation has been tried and measured, and each one is to
be brought back with before/after evidence rather than applied silently.

## Measured baseline

Full sweep, `tools/run_benchmarks.sh baseline-rs65-nf40 --render-scale=0.65 --near-scale=0.40`.
`vsync_actual=disabled`, `verdict_qualified=false` on every leg — these numbers are unqualified.

| leg | p50 | p95 | p99 | max | frames > 16.6 ms | gap to p99 target |
|---|---|---|---|---|---|---|
| steady | 23.61 | 25.00 | 26.17 | 31.10 | 100% | −9.6 |
| move | 10.61 | 29.17 | 32.41 | 35.51 | 25.3% | −15.8 |
| ridge | 24.38 | 33.33 | 37.54 | 44.26 | 100% | −20.9 |
| edit-bounded | 25.00 | 27.46 | 30.00 | 39.24 | 100% | −13.4 |
| island | 25.04 | 27.08 | 29.53 | 44.24 | 100% | −12.9 |
| *(edit, out of scope)* | *33.33* | *62.45* | *148.59* | *150.00* | *100%* | — |

## Attribution — steady leg, p50

Each row is a separate process, standard settle. Baseline measured three times to establish
noise: **24.01 / 23.61 / 23.81** → ±0.2 ms. Every delta below is far outside that band.

| variant | p50 | Δ vs 23.8 |
|---|---|---|
| off `ssao` | 15.15 | **−8.7** |
| `--quality=1` | 12.96 | −10.9 |
| off `near_field` | 11.67 | −12.1 *(not an option — it is the engine)* |
| off `raymarched_sun_shadow` | 21.67 | −2.1 |
| `--no-physics` | 21.67 | −2.1 |
| off `ssgi` | 22.73 | −1.1 |
| off `ssr` | 22.92 | −0.9 |
| off `outlines` | 23.33 | −0.5 |
| off `sun_shadow_map` | 23.81 | ~0 |
| off `glossy_sdf_rays` | 23.81 | ~0 |
| `--quality=2` | 23.61 | **~0** |

Two findings are load-bearing for this plan:

1. **SSAO is 37% of the frame** — more than raymarched sun shadow, physics, SSGI, SSR and
   outlines *combined*. It is also the only pass with no entry in `benchmark.gd`'s
   `BUDGETS_MS` table.
2. **`--quality=2` is indistinguishable from `--quality=3`.** `BeautySettings` carries
   `ssgi_taps`, `ssr_steps` and `contact_steps` but **no SSAO knob**, so
   `settings_for_tier(kMedium)` cannot scale the frame's single largest cost. Medium is a
   tier that costs what High costs.

## GPU-bound vs CPU-bound

`--no-physics` removes 5.1 ms of measured main-thread work but only 2.1 ms of frame time: at
p50 the frame is GPU-bound and CPU work hides behind it. CPU savings therefore surface almost
entirely at the spikes — which is where the p99 bar lives. Per-leg, the worst frames split
cleanly:

- **GPU-bound spikes:** ridge (44.26 ms) and move (35.51 ms) worst frames carry near-zero CPU
  counters (`phys_apply` 0.01 / 0.17, `stream_total` 0.07 / 0.08).
- **CPU-bound spikes:** island's 44.24 ms frame carries `phys_apply=10.53`; `island_ms` peaks
  at 26.44 ms.

## Workstreams

Ordered by measured value. Re-run the five-leg sweep after each and stop when all five hold
p99 < 16.6 ms.

### W1 — SSAO (expected −8.7 ms on every leg)

`shaders/ssao.comp.glsl` is full-resolution HBAO: `DIRECTIONS = 6` × `kSsaoSteps = 8`
(`ssao_pass.cpp:19`) = 48 samples per pixel, at 1592×857 ≈ 1.36 M px ≈ 65 M samples/frame.
Every sample does a depth fetch *and* a full `beauty_world_from_depth` world-space
reconstruction (inverse-view-projection multiply plus perspective divide).

Matched-image optimisations, in order of expected value:

1. **Sub-pixel early-out.** `pc.params.x` is a 5 m world radius. Past roughly 60 m that radius
   projects to under a pixel, so all 48 taps read the same texel and contribute nothing while
   costing everything. Compute `step_px` (already computed per direction, line ~70) and skip
   the direction when its total pixel extent is below ~1 px. On the ridge and steady cameras a
   large share of the screen is distant terrain, so this should be the single biggest win and
   is *exactly* output-preserving where it fires.
2. **View-space reconstruction.** Replace the per-tap world-space unprojection with a
   view-space reconstruct (linearise depth, scale by a precomputed ray). The AO math only
   needs relative offsets `dv = sp - p`, which are frame-invariant, so this is arithmetic
   reduction with no output change.
3. **Half-resolution + depth-aware upsample.** The shader header asserts a half-res chain
   "would fight the cel look for no win". That assertion is untested and worth testing, but it
   ranks below 1 and 2 because it is the first step here that can actually change pixels.

4. **Add an `ssao_steps` / `ssao_directions` knob** to `BeautySettings`, wire it through
   `settings_for_tier` and `clamp_settings` (mirroring the `ssgi_taps == 0 → ssgi = false`
   pattern), add an `ssao` entry to `BUDGETS_MS`, and expose it in `demo/settings_menu.gd`.
   This fixes the Medium-equals-High defect regardless of what the other steps deliver.

### W2 — LoD occlusion culling under motion (ridge, move)

`culled_ratio` is 0.238 on steady but **0.006 on ridge** and **0.000 at p50 on move**. The legs
that need occlusion culling are the ones not getting it.

Mechanism (`raymarch_compositor.cpp:290-365`): the two-phase path draws
`lod_cull->last_visible_pages()`, rebuilds HiZ from that, then culls the remainder against it.
`last_visible_pages_` is filled from an **async readback** (`consume_args_readback`), so under
continuous camera motion it describes a camera position several frames stale. The first pass
then draws the wrong set, the pyramid it builds is a poor occluder, and the cull that runs
against it rejects almost nothing.

Directions to investigate, cheapest first:
- Seed the first pass by **front-to-back page order** (sort by distance along view) rather than
  by the stale visible set, so the near ridge is guaranteed into the pyramid before the basin
  behind it is tested.
- Reproject the stale visible set to the current camera before using it.
- Confirm whether `hiz_built` is even true on these legs — it is gated on
  `near_field_enabled && hiz->build(...)`, and a silent failure here would produce exactly this
  signature. **Measure before changing anything.**

### W3 — CPU spike sources (island, edit-bounded, and every leg's max)

- **`commit_pending` is outside the budget guard.** `ColliderStreamer::run_frame`
  (`collider_streamer.cpp:481-520`) bounds the *build* path by `build_budget_ms_` at `:483` and
  `:514`, but the `next_octant >= kColliderOctants → commit_pending` branch at `:499` takes no
  budget check at all. A frame that
  commits eight octants pays unbounded main-thread time; `phys_apply` maxima are 27.05 (steady),
  22.97 (move), 18.63 (ridge), 35.00 (island), 48.07 (edit). Bring commit under the same wall
  clock, or amortise it across frames.
- **`run_connectivity` is synchronous on the main thread.** `IslandManager::run_frame` step 3
  (`island_manager.cpp:1266-1297`) runs a full connectivity relabel inline, unbudgeted;
  `island_ms` peaks at 26.44 ms. Move it to the mesh-service worker, or budget it.

### W4 — CPU steady cost (surfaces once W1 lowers the GPU floor)

`phys_collect` averages 2.4–4.6 ms and `phys_plan` 1.0–1.9 ms **every frame**. Today these hide
behind GPU work. After W1 removes ~8.7 ms of GPU time the CPU may become the critical path, at
which point they convert directly into frame time. Re-measure `--no-physics` after W1 to decide
whether this workstream is needed; do not pre-optimise it.

### W5 — Raymarched sun shadow (−2.1 ms)

`RAY_SHADOW_STEPS = 96` per hit pixel (`raymarch.comp.glsl:624`). The existing empty-region skip
is good; the remaining cost is step count. Only pursue if W1–W3 leave a gap, since reducing
steps risks visible shadow change.

## Budget math

Applying W1 alone (−8.7 ms, a full-screen pass so roughly constant across legs):

| leg | p99 now | after W1 | still needed |
|---|---|---|---|
| steady | 26.17 | ~17.5 | −0.9 |
| move | 32.41 | ~23.7 | −7.1 |
| ridge | 37.54 | ~28.8 | −12.2 |
| edit-bounded | 30.00 | ~21.3 | −4.7 |
| island | 29.53 | ~20.8 | −4.2 |

W1 is necessary everywhere and sufficient nowhere. Steady closes on W1 plus almost anything.
Ridge is the binding constraint and depends on W2 landing well; **if W2 underdelivers, ridge is
where a quality reduction gets proposed**, and that proposal comes back with evidence rather
than being taken unilaterally.

## Verification

- **Frame time.** Wall clock only. `debug_gpu_timings()` returns −1 for every per-pass field on
  this machine (`valid_samples=0`, confirmed again in every run of this baseline), so per-pass
  GPU attribution is unavailable and A/B against the whole frame is the only instrument.
- **Noise.** Three baseline runs per comparison point; the observed band is ±0.2 ms at p50.
  Any claimed win must exceed it. Never compare a single A run against a single B run.
- **Matched-image claims.** Characterise before refactoring: capture a golden via
  `--screenshot=` at a fixed camera *before* touching a pass, and diff after. A "matched image"
  claim without a diff is not a claim. This follows the repo's existing practice of a committed
  golden guarded by an exact test.
- **Do not verify render changes through `VoxelDebugHooks`.** `extension/src/debug/hooks.cpp`
  reconstructs render-path inputs rather than reading what
  `RaymarchCompositor::_render_callback` passes, so a green hooks-backed test can describe a
  path that does not ship. For W2 in particular, any test must read the compositor's own cull
  inputs.
- **gdUnit.** `./gdunit_tests.sh` has a standing, *drifting* set of failures on clean `main`.
  Before attributing any failure to this work, `git stash push`, re-run that same suite, and
  compare failure message text — not pass/fail counts.

## Risks

1. **Ridge may not close without a quality cut.** Biggest single risk; W2 is unproven.
2. **W2 may be a deeper design problem than a bug.** If correct culling fundamentally needs a
   non-stale visible set, the async readback design may need rework — that would be a larger
   project than this spec covers, and would come back for re-scoping rather than being absorbed
   silently.
3. **Metal presentation quantisation.** Observed frame times cluster on 1000/N values
   (25.00, 23.81, 16.67). Sub-16.67 values appear freely (11.67, 12.50, 12.96) so there is no
   60 fps cap, but measurements near the 16.6 ms boundary may quantise. Report p99 with the
   surrounding percentiles rather than a bare pass/fail.
4. **The 150 ms edit-leg frame is undiagnosed.** Near-zero CPU counters and a suspiciously round
   maximum. Out of scope for the guarantee, but it may share a root cause with the move/ridge
   GPU spikes; if W2 explains it, that is a signal the diagnosis is right.

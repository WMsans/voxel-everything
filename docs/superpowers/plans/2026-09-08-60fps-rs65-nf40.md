# 60 fps at render scale 65% / near field 40% — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Reach `p99 < 16.6 ms` on the steady, move, ridge, edit-bounded and island benchmark legs at `--render-scale=0.65 --near-scale=0.40`, without changing the rendered image unless a measured gap forces it.

**Architecture:** Fix in measured order, re-running the five-leg sweep after each landing. SSAO is 37% of the frame and comes first (Tasks 1–6). The LoD occlusion cull, which culls 0.6% on the leg built to exercise it, comes second (Tasks 7–8). Main-thread spike sources come third (Tasks 9–10). A final sweep decides whether steady-state CPU work still matters (Task 11).

**Tech Stack:** Godot 4.7.2, GDExtension (godot-cpp, C++20, `target=template_debug` → `-O2`), GLSL compute shaders via `RenderingDevice`, gdUnit4 for GDScript suites, `scons` for the native build.

**Spec:** `docs/superpowers/specs/2026-09-08-60fps-rs65-nf40-design.md`

## Global Constraints

- **Target config, verbatim:** `--render-scale=0.65 --near-scale=0.40`, resolution `2560x1440`, giving `internal_3d=1592x857`.
- **Bar:** `p99 < 16.6 ms` on **steady, move, ridge, edit-bounded, island**. The **edit** leg is explicitly excluded from the guarantee.
- **Machine:** Apple M1 (base, 8 GPU cores), macOS, Metal, 144 Hz display.
- **Measurement noise band is ±0.2 ms at p50.** Any claimed win must exceed it. Never compare one A run against one B run.
- **`debug_gpu_timings()` returns −1 on this machine** (`valid_samples=0`). Per-pass GPU attribution is unavailable; whole-frame wall-clock A/B is the only instrument.
- **Do not verify render changes through `VoxelDebugHooks` without checking the hook first.** `hooks.cpp` reconstructs render-path inputs for many entry points. `debug_ssao_probe` is an exception — it calls the real `SsaoPass::render` — and is therefore valid for Tasks 1–6. It does **not** run the compositor's two-phase LoD path, so it is invalid for Tasks 7–8.
- **gdUnit has a standing, drifting set of failures on clean `main`.** Before blaming any failure on this work: `git stash push`, re-run that same suite, compare failure *message text*, `git stash pop`.
- **Build after any C++ change:** `./build.sh`. Shaders load from disk at runtime and need no rebuild.

### Task 3: SSAO sub-pixel early-out

`pc.params.x` is a 5 m world radius. Past roughly 60 m it projects to under one pixel, so all `pc.dims.z` taps along a direction land in the same texel as the centre — `dv` comes out ~0, `len_sq < 1e-6` fires, and each tap contributes exactly nothing after paying for a texture fetch and an unprojection.

The existing guard is `dot(step_px, step_px) < 1e-9`, which only catches an exactly-degenerate direction. Raising it to `0.25` (i.e. `|step_px| < 0.5 px`) is **provably output-preserving**: the sampler is nearest (`SsaoPass::sampler_nearest_`), the largest tap offset along a direction is `step_px * 1.0`, and an offset under half a texel cannot change which texel `texture()` resolves to.

**Files:**
- Modify: `shaders/ssao.comp.glsl:71-73`

**Interfaces:**
- Consumes: `GOLDEN` from `tests/test_ssao_golden.gd` (Task 1).
- Produces: no interface change. Same push constant, same output texture.

```bash

```
Expected: the sampler is created with nearest filtering. The proof above depends on it; if it is linear, stop and use `0.01` (a strictly conservative value that still skips only degenerate directions) instead of `0.25`, and note it in the commit.

- [ ] **Step 2: Make the change**

In `shaders/ssao.comp.glsl`, replace:

```glsl

		if (dot(step_px, step_px) < 1e-9) continue;
```

with:

```glsl

		// with the largest tap offset below half a texel, every tap along this direction

		// texture fetches plus pc.dims.z unprojections per direction. Output-preserving.

```

### Task 4: Evaluate the unprojection incrementally

`beauty_world_from_depth` runs a full `mat4 * vec4` plus a perspective divide **per tap** — up to 48 per pixel. But `inv_view_proj * vec4(2u-1, 2v-1, d, 1)` is affine in `(u, v, d)`, and along a sweep direction `u` and `v` advance linearly while only `d` comes from the texture. So the `(u, v)` contribution can be evaluated once per direction and stepped, leaving one multiply-add plus the divide per tap.

Algebraically, with `M = bcam.inv_view_proj` and `uv_i = uv_0 + i * duv`:

```
M * vec4(2u-1, 2v-1, d, 1)
  = M[0]*(2u-1) + M[1]*(2v-1) + M[2]*d + M[3]
  = [M[0]*(2u_0-1) + M[1]*(2v_0-1) + M[3]]  +  i * [2*M[0]*duv.x + 2*M[1]*duv.y]  +  M[2]*d
  =                 h0                       +  i * dh                            +  M[2]*d
```

Exact, not an approximation.

- Modify: `shaders/ssao.comp.glsl:64-100` (the direction loop)

**Interfaces:**
- Consumes: `bcam.inv_view_proj` from `shaders/beauty_camera.glslh`; `GOLDEN` from Task 1.
- Produces: no interface change.

- [ ] **Step 3: Rewrite the tap loop**

In `shaders/ssao.comp.glsl`, replace the body from `float h_max = ...` through the end of the inner `for` loop with:

```glsl
		float h_max = asin(clamp(dot(n, dir3), -1.0, 1.0));

		// h(u,v,d) = inv_view_proj * vec4(2u-1, 2v-1, d, 1) is affine in (u,v,d), and along
		// this direction u and v advance linearly. Evaluate the (u,v) half once and step it;
		// only the depth column varies per tap. Same value, one mad instead of a mat4 mul.
		vec2 duv = step_px * bcam.screen.zw / float(pc.dims.z);
		vec2 uv0 = (vec2(px) + 0.5) * bcam.screen.zw;
		vec4 h0 = bcam.inv_view_proj * vec4(uv0.x * 2.0 - 1.0, uv0.y * 2.0 - 1.0, 0.0, 1.0);
		vec4 dh = bcam.inv_view_proj[0] * (2.0 * duv.x) + bcam.inv_view_proj[1] * (2.0 * duv.y);
		vec4 col_d = bcam.inv_view_proj[2];

		for (int i = 1; i <= pc.dims.z; i++) {
			vec2 suv = uv0 + duv * float(i);
			float sdepth = texture(gb_depth, suv).r;
			if (sdepth <= 0.0) continue;
			vec4 h = h0 + dh * float(i) + col_d * sdepth;
			vec3 sp = h.xyz / (abs(h.w) < 1e-9 ? 1e-9 : h.w);
			vec3 dv = sp - p;
			float len_sq = dot(dv, dv);
			if (len_sq < 1e-6 || len_sq > 4.0 * radius_sq) continue;
			float dn = dot(dv, n);
			float tangential = length(dv - n * dn);
			if (tangential < 1e-4) continue;
			float sin_h = clamp(dn / tangential, -1.0, 1.0);
			if (sin_h > h_max) {
				float r_sq = clamp(len_sq / radius_sq, 0.0, 1.0);
				occlusion += (sin_h - h_max) * (1.0 - r_sq);
				h_max = sin_h;
			}
		}
```

Note the `suv` expression now matches the `h` expression by construction — previously `suv` was rebuilt from `vec2(px) + 0.5 + step_px * (i / dims.z)`, which is the same value written differently. Keeping one definition removes the chance of the two drifting.
